`setH()` 的实现（`src/js/00_utils.js`）：

```js
function setH(el,html){
  if(!el)return el;
  const src=html==null?'':String(html);
  const frag=document.createRange().createContextualFragment(src);
  el.textContent='';
  el.appendChild(frag);
  el._h=src;          // 给「内容没变就别重画」的比较用
  return el;
}
```

解析出来的节点与原 innerHTML 完全一致，事件仍走委托，业务逻辑未改。

## 三·补、横屏版（含竖屏容器强制横屏）—— 已归档，未随 v4.1.0 重建

### 容器竖屏时的强制横屏

小红书容器按竖屏加载时 `orientation` 永远是 `portrait`，横屏媒体查询不生效。横屏包因此注入两段：

1. **CSS 旋转**：`@media (orientation:portrait)` 下把 `#app` 改为 `width:100vh;height:100vw`，`rotate(90deg) translateY(-100%)`，`transform-origin:top left`
2. **坐标换算**：`assets/rotate-input.js`（外置，head 内先于游戏脚本加载）

坐标换算的原因：`clientX/clientY` 报的是**视口坐标**，CSS 变换不会改变它。游戏按元素坐标算摇杆方向与落点，直接用会「上滑变右滑」。映射关系（顺时针 90°）：

```
元素 x = window.innerHeight - clientY
元素 y = clientX
```

在 `document` 捕获阶段覆写 `touches` / `changedTouches` / 事件本身的 `clientX clientY pageX pageY`，再让事件冒泡给游戏；只在 `orientation:portrait` 时生效。

实测（视口 542×900）：视口 `(280,900)`（底部中间）→ 元素 `(0,280)`（左侧中间）；视口 `(280,100)`（顶部）→ 元素 `(800,280)`（右侧）。方向映射正确。

## 四、兼容基线复核

| 特性 | 用量 | Chrome 61 表现 | 结论 |
| --- | --- | --- | --- |
| `clamp()/min()/max()` | 85 | 整条声明失效 | 47 处规则体全部有前置回退；`:root` 走 `@supports` 双份 + orientation 近似 `--vmin/--vmax` |
| `:has()` | 47 | 整条规则忽略 | 全部位于 `@media (orientation:landscape) and (max-height:560px)`，忽略后退回竖屏单列 |
| `dvh` | 3 | 忽略 | `height:100vh` 前置；变量增强包在 `@supports (height:100dvh)` 内 |
| `aspect-ratio` | 1 | 忽略 | `.btn.ico` 有 `min-height` 近似正方形回退 |
| `backdrop-filter` | 10 | 无前缀不支持（76+） | 均带 `-webkit-` 前缀或显式 `none` |
| `text-wrap:balance` | 1 | 忽略 | 纯排版增强 |
| flex `gap` | 36 规则 | **不支持（84+）** | **已知降级**：间距收紧、控件仍可点，不阻塞功能 |

> flex `gap` 未做自动兜底：每个容器方向（row/column）、换行与 `var(--gap)` 取值不同，批量生成 `margin` 兜底在 `flex-wrap` 场景会产生行首缩进，风险高于收益。真机容器（iOS 18.4 / 现代 Android WebView）均支持 `gap`，仅 8.1 未升级 WebView 会看到间距偏紧。
