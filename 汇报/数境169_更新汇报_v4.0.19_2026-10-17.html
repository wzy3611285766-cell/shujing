一、面板滑动：真凶是「每颗按钮一层模糊」

面板里每个按钮 / 选项 / 菜单项都挂着 backdrop-filter: blur(16px) saturate(180%)。滚动时它们的「底」一直在动，合成器就得每帧把几十层模糊全部重算一遍。

写了个探针（.tmp_play/_dbg_scroll.py）：开一个 40 行长面板，每帧把 scrollTop 推 6px，记 rAF 间隔；然后用注入的 CSS 一层层减，看哪一样真花钱。

条件（40 行列表 · 每帧滚 6px）帧间隔 p50相对现状
改前100 ~ 266 ms（3.7~10fps）—
只关行阴影100 ms0%
只关高光层100 ms0%
关掉所有阴影99.9 ms0%
关掉全部模糊16.7 ms（60fps）−83%
阴影和高光层一分钱都不是（0%）—— 如果靠猜，我会先去砍阴影，那就白改了。这也是为什么这类问题必须消融：主线程那 0.17ms 里根本没有它们的影子。

二、我上一轮的判断错了（记录在案）

4.0.17 我去掉了 HUD 的毛玻璃，但保留了面板与公告的全屏模糊，理由写进注释里：「面板一开地图就停画，那层模糊只算一次，不花钱」。

实测反过来：面板一滚动就要重新合成整屏模糊 —— 去掉它，100ms → 16.7ms。看不见的开销不能靠推理，只能靠测量。

顺带揪出三颗漏网的： 我用 :not(.primary) 保住金色主键的底色，结果把模糊也一起排除了 —— 整页还剩三颗金色主键挂着 blur(16px)（开机的「开始」、公告的「知道了」、面板的「确认」）。是「整页零毛玻璃」这条检查把它们揪出来的。

三、「画质」档位改管分辨率

毛玻璃既然默认全关，原来那一档「关毛玻璃」就无事可做了。现在它管像素预算：完整 180 万 / 流畅 ×0.8（89 万 → 57 万；线性 80% = 像素少 36%）。

这里踩了一步：只改预算的话，小屏（像素数本来就低于预算）完全没变化 —— 冒烟当场读出 888448 → 888448，红了一次。所以流畅档现在是「在算出来的 DPR 上再乘 0.8」，在任何设备上都有感。

四、云存档：读和写都没有按账号定位

「这份存档属于谁」原本前端完全没参与，全靠服务端行级权限兜。两台设备同一个手机号却拿到不一样的数据，最可能就是这里 —— 同一份两个人读，或者各读到不同行。

顺带补了个诊断：云存档面板现在会显示 云端存档：10月17日 14:22（来自「Android 手机」）· 128 分。两台设备对不上时先看这一行 —— 两边显示的云端时间 / 设备不一致，就不是「没同步」，而是读的不是同一份。

改前
  cloudPull:   db().from('saves').select(...).limit(1)            // 表里第一行
   push 兜底:   db().from('saves').select('id').limit(1) → update  // 改表里第一行
   upsert:      row 里没有 owner_id（指望服务端默认值）

改后
  ownerId()  = user.id || uid || sub || openid
  cloudPull:   …select(...).eq('owner_id', oid).limit(1)
  push:        row.owner_id = oid；兜底分支同样按 owner 查
  拿不到 id：  退回原行为，并在面板上写明「按账号定位失败」
这条修法依赖服务端的 owner_id 列与 SDK 的 session 形状，本地冒烟不联网，验不了。需要在两台设备上各开一次云存档面板，看「云端存档」那行是否同时间、同设备名。对不上把截图发我。
