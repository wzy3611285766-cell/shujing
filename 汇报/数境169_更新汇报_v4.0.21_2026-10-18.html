一、先复现：复现不出来

写了探针（tools/answerperf_plain.py）点正确选项，分三段量：处理器同步耗时 / 下一帧延迟 / 之后 2.5 秒的帧间隔。

项目无头环境实测
点击处理器同步耗时0.3 ms

说明问题不在手写逻辑本身，而在真机上某些调用很慢 —— 这类问题在本机测不出来，只能靠「真机上什么会慢」去推理，再用假慢去验证。

二、定位：副作用排在视觉写入之后同步跑

答对分支（改前）
  写 DOM（选项变绿 + #feedback + 下一步按钮）
  SFX.right()          ← 要唤醒 AudioContext（iOS / 安卓可能几百毫秒）
  lingJudge(...)       ← 读写觉醒存档

问题：这三步在同一个任务里。浏览器的绘制要等这个任务跑完，
于是「变绿」那一帧被后两步一起拖住 —— 玩家看到的就是「停一两秒才变色」。
改法就一句话：写入 → 这一帧画完 → 再做副作用。音效晚一帧（16ms），听不出来。

三、改法（注意一个坑）

烽火（59_interact.js）与闯关（39_hints.js）都改了。闯关那边把 save()/updateHUD() 也一起挪后 —— 它们同样是写入之后的同步开销，而存档每 5 秒还会再存一次，不差这一帧。

fb.className='ok'; fb.innerHTML=…; nextBtn.style.display='block';
const sideFx = ()=>{ SFX.right(); lingJudge(…); };
requestAnimationFrame(()=>setTimeout(sideFx,0));

// ⚠️ 必须 rAF + 宏任务 两段：
//   rAF 回调跑在**这一帧绘制之前** —— 只用 rAF，慢副作用照样挡在绘制前面。
//   先等下一帧开始（上一帧已提交），再用 setTimeout 排到这一帧之后。

四、决定性实验：把音效换成忙等 800ms

只改代码不算证明。把 SFX.right 换成一个忙等 800ms 的空函数（模拟真机唤醒音频的代价），量「点击 → 反馈上屏」（tools/answerperf.py）：

版本点击同步耗时反馈上屏
改前 v4.0.20800.3 ms800.4 ms
改后0.3 ms8.1 ms
中间踩了一次度量错误：一开始用「两次 rAF」当上屏时刻，结果第二次 rAF 自己也被副作用挡住，改后照样读出 820ms。
改成只等一帧才对（DOM 写在 click 里就完成了，这一帧画出来的就是带反馈的画面）。度量口径错了，结论会反着来。

五、给真机留一格读数

?dbg=1 面板最后新增一行：答题反馈 Xms —— 从写入到真的画到屏幕上隔了多久（答题路径写入 window.__ansGap）。

真机上如果这格是几百毫秒，说明还有别的东西在拖（比如面板本身的重排、或者别的音效），把截图发我继续查；如果是十几毫秒，那这次改的就是那一处。
