平板帧率修复报告

2026-10-14 · 定位到「vivo Pad 2 拖摇杆掉帧」的根因是画布分辨率 4 倍 + 每帧预算只有 6.9ms · 改了 3 处渲染 + 加了一个 ?dbg=1 诊断角标 · 弱机模拟：平板地图 1.6～1.7 倍，手机零回归

一、先把账算清楚：为什么只有平板卡

三台设备的 SoC 其实是同一档（天玑9000 / 天玑9200，GPU 是 Mali-G710 与 Immortalis-G715，差距 20% 上下）。真正的差距在三个地方：

设备屏幕刷新率游戏后备画布每帧预算
vivo X90 Pro6.78" 2800×1260 = 353 万像素120Hz786×1750 = 138 万8.33ms
vivo Pad 212.1" 2800×1968 = 551 万像素144Hz2800×1968 = 551 万6.94ms
电脑—60/144Hzdpr 一般 ≤1.5，且 GPU 余量大16.7ms

关键在于这条上限只保护了手机

DPR = Math.min(window.devicePixelRatio || 1, 2);   // 改之前
  • 手机要维持 393dp 左右的显示宽度，devicePixelRatio 必然是 3.2 上下 → 被压到 2， 等于只用 62% 分辨率渲染。这才是手机一直很流畅的隐藏原因。
  • 而 12.1 寸平板（2800px 宽 / 系统默认密度正好 = 2）压不动：后备画布 2800×1968， 是手机的 4.0 倍；再乘刷新率 144/120 = 每秒 4.8 倍的主线程光栅化工作量， 每帧预算反而少 17%。
所以卡顿的根源不是平板弱，而是它在「原生分辨率 + 144Hz」下跑同一份代码。 硬件只差一档，工作量差 4～5 倍 —— 拖动摇杆时每帧都在重画整张画布，就直接崩了。

二、改了三处

① 画布分辨率改成「按像素预算」

不再问 devicePixelRatio 是多少，而是问我这台机器一帧画得起多少像素：预算内一分不降，超了就按面积开方降 dpr。

const PIX_BUDGET = 1800000;   // CSS 像素 × DPR²，约等于「手机竖屏现状」那一档
DPR = clamp(Math.sqrt(PIX_BUDGET / Math.max(1, VW*VH)), 1, Math.min(devicePixelRatio||1, 2));
设备CSS 视口算出来的 dpr后备画布相对改动前
vivo Pad 2 横屏1400×9841.141600×1124（181 万）光栅化工作量 −66%
手机竖屏430×9322.00860×1864（160 万）不变

画质代价很小：#game 上只有地面光晕、影子、角色圈、小地图这些没有细节的东西； 文字和 emoji 全在 DOM 实体层，不经过这张画布（地形是另一层，分辨率完全没动）。

② 渲染节拍器：不再「每次 rAF 都画」

144Hz 每帧只有 6.9ms 预算。画不完时浏览器会跳过若干 vsync 再交下一帧，间隔变成 「等 2 个 vsync、等 3 个 vsync」交替 —— 眼睛看到的就是一顿一顿。 与其贴着刷新率忽快忽慢，不如稳稳地每 2 个 vsync 出一帧。

const k = Math.round((now - PERF.last) / PERF.vs);   // 隔了几个 vsync（不是比毫秒）
if (k < PERF.multi) return;                          // 没到点：这一帧不画
...
if (PERF.n >= 30 && PERF.hz > 0) {                  // 每 30 帧评一次档
  const budget = PERF.vs * PERF.multi;
  if (PERF.work > budget*0.8 || 迟到帧 > 25%) PERF.multi++;   // 降一档
  else if (连续 6 批都只用 <40% 预算)          PERF.multi--;   // 升一档
}
  • 档位只取 vsync 的整数倍：144Hz → 144/72/48/36/24，120Hz → 120/60/40/30/24，60Hz → 60/30/20/15。 任何屏幕上帧间隔都完全均匀 —— 顺带解决一个老问题：144 除以 60 除不尽，硬塞 60fps 会 2 帧/3 帧交替。
  • 量不出节拍（hz=0）时不升降档，游戏照「每帧都画」跑，跟改之前一样； 开机先按 144Hz 假设，所以不会出现「还没量准就先掉帧」。
踩到并修掉的坑：第一版用「窗口内最小 rAF 间隔」当 vsync，结果一次偶发的 3～4ms 抖动把节拍记成 250Hz，档位表整张崩掉（实测渲染从 19fps 掉到 15fps）。现在两条防呆：间隔 <5ms 不算数、 同一个最小值必须在一窗口里出现两次以上才采纳。

③ 地形层的位移吸附到整数设备像素

const rd = window.devicePixelRatio || 1;
const tx = (Math.round(-cam.x*SCALE*rd)/rd).toFixed(3);
bgCv.style.transform = 'translate3d('+tx+'px,'+ty+'px,0) scale('+SCALE+')';   // 原来是 toFixed(2)

地形层每帧都要被合成器重采样一遍：位移带小数时采样点永远落在纹素之间，纹理在像素网格上逐帧「游走」， 拖动时地形会持续发糊、闪。吸附之后采样点正好落在纹素中心。误差 ≤0.5 设备像素 = 0.25 CSS 像素，肉眼不可见。

四、新增：?dbg=1 诊断角标

平板上没有 devtools，看不到 devicePixelRatio、后备画布多大、一帧到底花了几毫秒。 在网址后面加 ?dbg=1 就会在屏幕左侧出现一个角标：

画布 1600×1124后备画布像素 = 每帧要光栅化的量
节拍 30Hz? 抽1实测 rAF 节拍 / 每几帧画一帧
每帧 4.6ms/33.3ms主线程耗时 / 这一档的预算
迟到 10/12本批评里迟到的帧数

三条读数规则

  • 「每帧」长期贴着「预算」 → 是每帧画不完，该继续降分辨率（PIX_BUDGET 还能往下调）。
  • 「节拍」带问号（比如 30Hz?）→ 那不是屏幕变慢了，而是这台机器跑不満屏幕； 常见值 60/90/120/144/165 才不会打问号。
  • 「渲染」明显低于「节拍÷抽帧数」 → 主线程被别的东西拖住了（这个角标自己半秒才刷一次，不会反过来影响读数）。
角标只在带 ?dbg=1 时创建，元素和样式都在 JS 里注入，正常玩家看不到、也不占 HTML/CSS 模块。

六、还没做的 & 玩家侧能做的

代码侧（下一轮，收益递减）

  • 实体层降载：entDraw() 每帧给每个实体无条件写 style.transform（144Hz 下每秒约 9 千次样式写入 + 字符串拼接）。 改成「位移变化 <0.5px 就不写」，能省一截主线程时间。
  • 输入合并：pointermove 只记最后一个点、在 rAF 里消费；拖摇杆时避免任何布局读取。
  • 画质档位：给玩家一个「流畅优先」开关（= 手动把 PIX_BUDGET 降到 120 万）， 比让他去改系统设置友好得多 —— 顺带说明：页面里 viewport 写了 user-scalable=no， 玩家没有任何办法自己降分辨率，这个杠杆只能在代码里给。

玩家侧（不改代码就能试的）

  • 把系统刷新率切到 60Hz 再拖摇杆：如果明显好转，就印证了「每帧预算不够」这条 —— 这是最省事的判断针（144Hz 只有 6.9ms，60Hz 有 16.7ms）。
  • 关掉省电模式 / 自适应刷新率（系统在负载波动时来回切档，会变成忽快忽慢）； 确认浏览器在「高刷应用名单」里；换 Chrome 内核对比一下自带浏览器。
  • 关分屏 / 小窗 / 后台应用；别边充边玩（温控降频）。
  • 同一台平板竖屏比横屏更重：竖屏 SCALE 1.59 > 横屏 1.14，每世界单位占更多设备像素，地形层放大倍率更高。
