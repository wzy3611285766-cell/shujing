一、公告看不到：一条 4.0.9 的分支在静默跳过它

当初的理由是「他连上次是什么样都不知道，一上来读更新要点没意义」。玩家的反馈很直接：一点开先被塞一段闯关介绍，公告反而看不到。

现在这条删掉：公告照常弹 → 关掉之后 `maybeIntro` 再弹首访说明。它本来就等着公告关掉（`newsSeen()/newsIsOpen()` 轮询），所以顺序天然是对的，错的只是「公告被跳过」这一半。

顺带：重试时原来还带着初始的 700ms 延时 —— 实测「关掉公告 → 说明出现」要 1 秒多，看着像卡住。现在重试传 150ms，约半秒就到。

// 改前（newsBoot）
if(newsSeen())return;
/* 全新玩家先看教学，不看「这次改了什么」 */
try{
  if(!localStorage.getItem(curKey+'_intro') && isNewPlayer()){
    markNewsSeen();      // ← 公告被记成已读
    return;              // ← 于是永远不弹
  }
}catch(e){}

二、帧率角标：默认从关改成开（但别翻掉别人手动关的）

function fpsBadgeOn(){
  const v = localStorage.getItem(FPS_KEY);
  return v===null ? true : v==='1';   // 没存过 → 开；存过 → 照存的来
}
// 读取抛异常（无痕模式）→ 也当首次，开
☰ 菜单里那一项没变（「帧率角标：开/关」），切完会记住。手动关过的人不会被翻回来 —— 这是默认值开关最容易踩的坑。

三、两条永久检查（这才是这类改动的价值）

①「首屏顺序」： 帧率角标默认必须是开、关掉后必须能记住、#fps 元素必须真的挂上；并且 newsBoot 的函数体里不许出现 markNewsSeen。那条定时器是异步的、同步单测等不到，所以直接钉住「公告不能被静默标已读」这条规则。
②「首访说明只弹一次」改成正向断言： 全新玩家必须先看到公告、公告开着时不许同时弹说明、关掉公告之后说明必须出现、公告不能在没看之前被记已读。
原来这条检查钉的是旧规则（「全新玩家不该看到公告」），改需求后它一起红了 —— 检查里写着旧规矩，改需求时正好提醒你「这里有东西要一起改」。
